1 — Overview

flowToApexAI converts Salesforce automation in both directions using Einstein Generative AI. Everything runs inside the org — no external services, no CLI after deploy.

DirectionInputOutputAuto-deploy?
Flow → Apex Record-Triggered Flow API name Apex handler class implementing IFlowMigrationHandler Yes — handler deployed + CMT registered automatically
Apex → Flow Apex handler class name Deploy-ready .flow-meta.xml or a refusal with reason No — copy the XML and deploy via SF CLI or Setup
Einstein Trust Layer All AI calls go through Salesforce Prompt Builder and stay within your org's Einstein Trust Layer boundary. No data leaves Salesforce.

2 — Architecture

User (Lightning App — "Flow to Apex AI")
   │
   ▼
LWC: flowToApexConverter          ◄── direction toggle
   │
   ├── Flow → Apex path
   │     FlowReaderService         Tooling API → reads Flow JSON
   │     EinsteinPromptClient      Prompt Builder → Einstein
   │     ApexDeployService         Tooling API → creates ApexClass
   │     insert FlowMigration__c   persists result
   │     ApexDeployService @future Metadata.Operations → Trigger_Handler__mdt
   │
   └── Apex → Flow path
         ApexSourceReaderService   Tooling API → reads Apex body
         EinsteinPromptClient      Prompt Builder → Einstein
         insert FlowMigration__c   persists result (XML or refusal)

── Trigger dispatch (Flow→Apex result) ───────────────────────────────────────
AccountTrigger → AccountTriggerDispatcher.dispatch()
   └── SELECT Handler_Class__c FROM Trigger_Handler__mdt
         WHERE Object__c = 'Account' AND Active__c = true
         ORDER BY Order__c ASC NULLS LAST
           └── Type.forName(Handler_Class__c).newInstance()
                 → IFlowMigrationHandler.run(op, records, oldMap)

Key design decisions

DecisionWhy
Callouts before DML Salesforce prohibits callouts after DML in the same transaction. All Tooling API + Einstein calls happen first.
CMT registration in @future Metadata.Operations.enqueueDeployment() (setup object) cannot run in the same transaction as insert FlowMigration__c (non-setup). @future isolates the two.
Skip PATCH on existing class Tooling API PATCH on a metadata-deployed ApexClass requires a MetadataContainer workflow. We skip the update — existing class body is preserved, CMT registration still runs.
CMT-based dispatch One trigger per object, never modified. New handlers register via a metadata record — zero code changes to the dispatcher.
SessionIdPage VF Tooling API self-callouts require a REST-valid session ID. Lightning sessions are not REST-valid; the VF page surfaces one.

3 — Prerequisites

  • Einstein Generative AI enabled — Setup → Einstein Setup → turn on Generative AI.

  • Prompt Builder enabled — Setup → Einstein → Prompt Builder → enable.

  • Two Prompt Templates created in Prompt Builder:

    Template API NameInput VariableSource File
    Flow_To_Apex_ConverterflowMetadata (Free Text)docs/prompts/Flow_To_Apex_Converter.txt
    Apex_To_Flow_ConverterapexSource (Free Text)docs/prompts/Apex_To_Flow_Converter.txt

    Paste the file content into the template body. The API name must match exactly (case-sensitive).

  • Remote Site Setting — Setup → Remote Site Settings → add your org's My Domain URL (e.g. https://myorg.my.salesforce.com). Required so Apex can call the Tooling API on the same org.

4 — Deploy to Org

Run from the project root:

sf project deploy start \
  --source-dir force-app/main/default \
  --target-org <orgAlias>
What gets deployed Apex classes + triggers + dispatchers, LWCs, FlowMigration__c custom object, Trigger_Handler__mdt CMT type, two seed CMT records for the existing Account handlers, Visualforce SessionIdPage, custom tabs, Lightning App.

5 — Post-Deploy Setup

  • Field-Level Security — Grant Read (and Edit where appropriate) on all FlowMigration__c fields to the running user's profile or permission set.

    Fields: Source_Flow_Name__c, Object_Name__c, Direction__c, Status__c, Generated_Apex__c, Generated_Flow_XML__c, Error_Message__c, Deploy_Status__c.

  • Page Layout — Add Direction and Deploy Status fields to the Flow Migration page layout if you want them visible on the record detail page.

  • Verify Prompt Templates — In Prompt Builder, open both templates and run a quick test to confirm Einstein responds without errors.

6 — Using Flow → Apex

Step-by-step

  • App Launcher → Flow to Apex AI.

  • Direction toggle: select Flow → Apex (default).

  • Enter the Flow's API Name exactly as it appears in Setup → Flows (e.g. Account_Set_Default_Industry). The Flow must be a Record-Triggered Flow and must be active.

  • Click Convert. The spinner shows "Converting — this can take 10 to 30 seconds."

  • Result appears inline. On success:

    • The generated handler Apex class is shown with a Copy button.
    • ✓ Deployed & registered in Trigger_Handler__mdt — active on next trigger fire.

What happens automatically

  1. Einstein reads the Flow JSON via the Tooling API.
  2. The handler class is created in the org via Tooling API POST to /services/data/v59.0/tooling/sobjects/ApexClass.
  3. A FlowMigration__c record is inserted with Direction = Flow_To_Apex and Deploy_Status__c = Deployed.
  4. In a separate @future call, a Trigger_Handler__mdt record is created via Metadata.Operations.enqueueDeployment().
  5. On the next trigger fire for the relevant object, the CMT-based dispatcher instantiates the handler by name and calls run().
Zero manual steps You do not need to edit any dispatcher class, run sf deploy, or create any metadata record manually.
Existing class detected If a class with the same name already exists in the org (e.g. from a prior deploy or a previous conversion), its body is not overwritten. The CMT registration still runs so the dispatcher picks it up.

Auto-deploy failed

If the badge shows Auto-deploy failed:

  • The error detail is shown below the badge.
  • The generated handler code is still shown — copy it and deploy manually via SF CLI or Developer Console.
  • Then create a Trigger_Handler__mdt record manually (see Section 9).

7 — Using Apex → Flow

Step-by-step

  • In the converter, switch the direction toggle to Apex → Flow.

  • Enter the Apex class name (e.g. AccountSetDefaultIndustryHandler). The class must exist in the org and implement IFlowMigrationHandler.

  • Click Convert.

  • Three possible outcomes:

    ResultMeaning
    Flow XML generatedA .flow-meta.xml is ready to copy and deploy.
    Not translatableThe handler uses a pattern Flow cannot express. A plain-English reason is shown.
    Conversion failedAn unexpected error occurred (see error message).

Deploying the generated Flow XML

  1. Copy the XML from the result panel.
  2. Save it as <FlowApiName>.flow-meta.xml in your SFDX project.
  3. Deploy: sf project deploy start --metadata Flow:<FlowApiName> --target-org <alias>
  4. Activate the Flow in Setup → Flows if it deploys as Inactive.

Patterns that cannot be translated to Flow

The converter refuses when the handler uses:

  • try / catch blocks
  • @future, Queueable, Batchable
  • HTTP callouts
  • Dynamic SOQL
  • Recursive methods
  • Custom exception classes
  • SOSL queries
  • Schema describe calls
  • Multi-object DML in same branch
  • Complex string parsing / regex
  • Non-Id keyed Maps used as lookup tables
  • Mixed before-save + after-save op gates

8 — Migration Records (FlowMigration__c)

Every conversion — success or failure — is persisted as a FlowMigration__c record. Click Open Migration Record in the result panel or browse the Flow Migrations tab.

  • Source_Flow_Name__cAPI name of the source Flow or Apex class.
  • Direction__cFlow_To_Apex or Apex_To_Flow.
  • Object_Name__cSObject the handler operates on (e.g. Account).
  • Status__cNew → Generated or Failed.
  • Generated_Apex__cFull Apex class body (Flow→Apex only).
  • Generated_Flow_XML__cFull .flow-meta.xml (Apex→Flow only).
  • Error_Message__cStack trace on failure, or refusal reason on NotTranslatable.
  • Deploy_Status__cDeployed, Deploy_Failed, or Not_Attempted (Flow→Apex only).

9 — Handler Registry (Trigger_Handler__mdt)

Every generated handler is registered in Trigger_Handler__mdt automatically. You can view, disable, or reorder handlers without touching any Apex code.

Setup → Custom Metadata Types → Trigger Handler → Manage Records.

  • Object__cSObject API name the handler belongs to (e.g. Account).
  • Handler_Class__cFully-qualified Apex class name (e.g. AccountSetDefaultIndustryHandler).
  • Active__cCheckbox. Uncheck to disable a handler without deleting the record.
  • Order__cExecution order per object. Lower numbers run first. Null values run last.

How the dispatcher uses this registry

// Each dispatcher (AccountTriggerDispatcher, etc.) runs:
List<Trigger_Handler__mdt> handlers = [
    SELECT Handler_Class__c
    FROM   Trigger_Handler__mdt
    WHERE  Object__c  = 'Account'
    AND    Active__c  = true
    ORDER BY Order__c ASC NULLS LAST
];
for (Trigger_Handler__mdt h : handlers) {
    IFlowMigrationHandler inst =
        (IFlowMigrationHandler) Type.forName(h.Handler_Class__c).newInstance();
    inst.run(Trigger.operationType, Trigger.new, Trigger.oldMap);
}
Supported objects Dispatchers are included for Account, Contact, Lead, Opportunity, and Case. Adding a new object requires creating a new trigger + dispatcher following the same pattern.

Manually creating a CMT record

If auto-deploy failed and you deployed the handler class manually:

  1. Setup → Custom Metadata Types → Trigger Handler → Manage Records → New.
  2. Label: handler class name (max 40 chars). Developer Name: auto-generated or set manually.
  3. Object: the SObject API name. Handler Class: exact class name. Active: checked. Order: any number.
  4. Save. Active on next trigger fire.

10 — Troubleshooting

Auto-deploy failed — insufficient access rights on cross-reference id

The handler class already exists and was deployed via metadata (SFDX). The Tooling API cannot PATCH metadata-deployed classes. This is expected — the class is already in the org. The CMT registration still ran (or will run). Check if the Trigger_Handler__mdt record was created; if not, create it manually (Section 9).

CMT registration failed — mixed DML

DML operation on setup object is not permitted after you have updated a non-setup object.
This should not happen with the current code because CMT registration runs in an @future context. If you see it, check that you are running the latest version of ApexDeployService.

Conversion failed — Unknown error

Open browser DevTools → Console. The LWC logs the full error object as JSON. Common causes:
  • Prompt Template not found — verify API name matches exactly (case-sensitive).
  • Einstein Generative AI not enabled — check Einstein Setup.
  • Remote Site Setting missing — add your org's My Domain URL.
  • FLS — running user cannot read/write FlowMigration__c fields.

Handler not firing after conversion

  • Verify the Trigger_Handler__mdt record exists and Active__c = true.
  • The CMT record is created asynchronously (@future). Wait a few seconds after the "Deployed" badge appears.
  • Check that the correct trigger exists for the object (AccountTrigger, etc.).
  • Verify the handler class exists in the org (Setup → Apex Classes).

Flow → Apex: "Flow API name is required"

Enter the Flow's API Name, not its label. Find it in Setup → Flows → click the Flow → the URL contains the API name, or check the Flow's properties.

Apex → Flow: "does not match IFlowMigrationHandler signature"

The Apex → Flow converter only works on handlers that implement IFlowMigrationHandler with the exact run(op, List<SObject>, Map<Id,SObject>) signature. Standard Apex classes with other shapes are not supported.
