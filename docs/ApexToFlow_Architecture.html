5. Pattern Classification

Must Refuse — NOT_TRANSLATABLE
  • try / catch blocks
  • Dynamic SOQL (Database.query)
  • @future, Queueable, Schedulable, Batch
  • Recursive method calls
  • HTTP callouts (HttpRequest)
  • Custom exception classes
  • Anonymous inner classes
  • Complex string parsing / regex
  • Map<non-Id, V> used as lookup table
  • Set<non-Id> de-duplication
  • Multi-SObject DML in same branch
  • Nested loops with shared accumulators
  • SOSL (FIND … RETURNING)
  • Schema.getGlobalDescribe
  • System.enqueueJob / schedule
Always Translatable — Never Refuse
  • Map<Id, SObject> as bulk-DML collector
    (loop fills → single update outside)
  • Set<Id> for SOQL WHERE Id IN :ids
  • if / else if / else chains (any depth)
  • for (SObject sObj : soqlResult) loops
  • record.FieldName = value assignments
  • oldMap.get(record.Id) comparisons

6. Key Design Decisions

Why List<SObject> + cast instead of List<Account>?

The interface IFlowMigrationHandler requires a generic signature. The trigger object is identified from the cast inside the loop body: Account record = (Account) sObj. The cast line is the type declaration — the prompt looks one level deeper than before.

Why does ===STATUS=== come first in the output?

The parser uses indexOf(), not line order. But having STATUS first puts the model in a "decision made, fill in the details" mode — this empirically reduces hallucinated XML when the correct answer is NOT_TRANSLATABLE.

Why an explicit "ARE translatable" whitelist?

Without it, the model refuses Map<Id, SObject> bulk-collectors and Set<Id> patterns because they look "complex." The whitelist prevents false negatives on patterns that round-trip cleanly between Apex and Flow.

Why is mixing BEFORE + AFTER a hard refusal?

Flow's triggerType accepts exactly one value — before-save or after-save, never both. Apex can gate on BEFORE_INSERT + AFTER_UPDATE legitimately, but there is no valid Flow representation — refusing is the only honest answer.

7. Response Parsing — ApexToFlowService

raw model response
│
├── section("===STATUS===", terminators=[OBJECT, FLOW_XML, REASON])
│     → "TRANSLATABLE" or "NOT_TRANSLATABLE"
│
├── section("===OBJECT===", terminators=[FLOW_XML, REASON])
│     → "Account" (stored in FlowMigration__c.Object_Name__c)
│
├── section("===FLOW_XML===", terminators=[REASON])
│     → full XML string (stored in Generated_Flow_XML__c, max 131 072 chars)
│
└── section("===REASON===", terminators=[])
      → refusal text (stored in Error_Message__c)

Decision logic:
  isTranslatable = STATUS contains "TRANSLATABLE" AND NOT "NOT_TRANSLATABLE"

  if isTranslatable && xml present  →  Status__c = 'Generated',  flowXml saved
  if !isTranslatable && reason present →  Status__c = 'Failed',    reason saved
  if xml present but STATUS unclear  →  accept xml (fallback)
  else                               →  throw EinsteinClientException

8. Required Flow XML Shape

<?xml version="1.0" encoding="UTF-8"?>
<Flow xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>59.0</apiVersion>
    <label>{FlowLabel}</label>
    <interviewLabel>{FlowLabel} {!$Flow.CurrentDateTime}</interviewLabel>
    <processType>AutoLaunchedFlow</processType>
    <runInMode>DefaultMode</runInMode>
    <status>Active</status>
    <start>
        <locationX>50</locationX>
        <locationY>0</locationY>
        <connector><targetReference>{firstElement}</targetReference></connector>
        <object>{SObject}</object>
        <recordTriggerType>Create</recordTriggerType>
        <triggerType>RecordBeforeSave</triggerType>
    </start>
    <!-- elements: decisions · assignments · recordLookups
                   recordCreates · recordUpdates · recordDeletes · loops -->
</Flow>

Layout: locationX=50 fixed, locationY starts at 0.
        Each subsequent element: locationY += 150.
        Decision branches: locationX ± 200.
